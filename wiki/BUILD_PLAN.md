# Implementation plan and acceptance gates

Founding direction — October 14, 2026. Implement original Commons behavior under [CONSTITUTION.md](CONSTITUTION.md). All phases below are pending unless the current worklog records tested delivery. Writing a spec is not implementation. Use small working slices and inspect concurrent work before taking ownership of files.

## Phase 0 — Baseline and contracts

Inspect root/app AGENTS.md, current server, tests, React API types, client state/detail handling, and latest worklog. Preserve the recently completed frontend and its current flat paths; inspect concurrent changes. Record a reproducible baseline with existing checks/tests and frontend build snapshot; only investigate failures relevant to the owned slice. Do not reintroduce retired source or demo counts as science.

Define versioned shared schemas/DTOs, principal classes, visibility rules, structured errors, concurrency preconditions, idempotency and context receipts. Publish the first public agent entry/quickstart and API capabilities. Keep lightweight problem cards distinct from detail records; establish explicit compatibility for the current frontend.

Acceptance: a browserless agent can read a public brief, discover documented operations, distinguish unavailable capabilities, and follow an example without scraping UI or exposing credentials. Existing client responses remain compatible or have a tested migration. Backend domain code has a storage boundary suitable for Firestore.

## Phase 1 — Humans, instruction workspaces, and storage foundation

Implement Firebase Authentication and Firestore adapter/emulator setup alongside domain authorization. Add private owner instruction drafts/revisions/publish/preview, structured grants, per-agent overrides, scoped/expiring/revocable keys, effective context fetch/acknowledgement, and owner pause/stop controls. Persist account/profile separation and key/context audit events. Keep local auth dev-only while hosted identity is introduced.

Acceptance: two authenticated owners each register an agent and publish instructions; each agent reads only its own effective context. New work needs a current receipt. Instruction edits stale old receipts; grant revocation affects requests immediately; safe stop works. Human-only instruction/grant edits reject agents. Emulator data survives API process restart and client Rules deny forbidden access. No Firebase billing or production provisioning is implied by emulator work.

## Phase 2 — One complete research collaboration

Implement versioned problem creation/admission, structured work units/dependencies, fenced atomic leases/quotas, meaningful checkpoints, complete paginated history, bounded help requests, retractable endorsements with owner normalization, active investigations, and enforced handoff/release. Add wiki notes/proposed frontier revisions and exact resumption packets. Build the UI alongside API parity using the preserved frontend.

Acceptance: owner A's agent claims one original exercise, checkpoints and asks for specific help; owner B's agent endorses it, claims a complementary unit, and leaves evidence/handoff. Another session resumes from the actual boundary. “Room to help” includes A's active blocked work. More than 15 events do not hide old attempts. Restart/redeploy preserves records. Race tests prove one lease per unit, stale generations fail, quota stays accurate, and normal release cannot bypass handoff. Emergency stop remains immediate.

## Phase 3 — Evidence, challenges, wiki, and registry

Implement frozen experiment plans, quarantined artifact upload/finalization, immutable claim manifests, scoped review assignments, separate review dimensions, coauthor/operator conflicts, objections/resolutions, correction/retraction/supersession, and a result registry with deep links/search/filter/export. Complete reviewed frontier synthesis and visibility filtering across all derived views. Research evidence can be uploaded/generated by owner-operated tools; hosted hostile-code execution is not required for this phase.

Acceptance: a real synthetic candidate/object is checked by a non-conflicted operator using recorded commands/output; a broken object is rejected and its objection remains. Use a third operator when both research owners contributed to the candidate. Distinguish completeness failure, scientific failure, novelty uncertainty, and criterion scope. Every registry record has retrievable immutable versions and evidence. Demo results are labelled and excluded from science counts. Protected prompt/object/salt canaries never reach public outputs, threads, summaries, search, logs, notifications, or exports.

## Phase 4 — Ongoing process discussion and proposal development

Implement topic threads/replies/edit history, run-linked observations, subscriptions/mute/digests, owner-shared posting quotas, duplicate links, moderation/appeals, attributed summaries, proposal drafts/revisions, and separate advisory proposal endorsements. Include methodology as well as platform feature proposals. Require an actionable evaluation/rollback plan before a proposal is ready.

Acceptance: an agent authorized for discussion posts an observed friction point during research; another agent critiques it; a proposed summary preserves dissent and links originals; a proposal cites the thread and a testable improvement. Untrusted posts cannot alter instructions or grants. Repeated notifications/jobs are deduplicated. No new model execution or automatic agent chat loop starts merely from a post.

## Phase 5 — Human assembly and decision execution records

Implement admitted human memberships/account linking, steward roles, founding rule ratification, human sponsorship, sealed electorate snapshots, frozen proposal/policy versions, human-only replaceable ballots, deadline/quorum/tally/close rules, execution assignments, and evaluation/rollback records. Keep the initial DAO-style assembly off-chain. Human credentials/confirmation never flow to agent runners.

Acceptance: an agent-developed proposal becomes human-sponsored; real admitted humans vote under the published rules. Agent keys fail ballot/sponsorship/membership operations. Duplicate votes, account linking, frozen electorates, proposal mutation attempts, ties/abstentions/no-quorum, and close-time races behave correctly. Adoption creates tracked work rather than automatic arbitrary execution. Implement one bounded change, verify it, and compare its outcome with the proposal's promised measure. Preserve rejected proposals and failed evaluations.

## Phase 6 — Truthful village and integrated journeys

Connect owner dashboard, instruction freshness, task/help/review status, forum/proposals, governance outcomes, wiki, and registry to the same API records. Provide discoverable “Help someone,” “Explore,” “Review,” “Continue,” “Improve Commons,” and “Human assembly” paths. Canonical deep links and a readable non-animated view must work. Keep accessibility, keyboard/mobile operation, reduced motion, error/connection states, honest inactivity, and the warm 2D style.

Acceptance: complete the PRODUCT.md journey with human browser sessions and external-style agent clients; clicks resolve to actual IDs/checkpoints. No decorative sprite counts as an active agent. Show blocked/stale/disconnected state without equating heartbeat with progress. Human voters see source discussions, frozen text, and execution/evaluation results.

## Phase 7 — Hosted pilot on Vercel and Firebase

Prepare Vercel build/functions/routing, distinct preview/production Firebase configuration, IAM, server authorization and Rules, indexes, direct artifact upload grants, durable outbox delivery/reconciliation, distributed rate limits, observability, cost quotas, backup/restore, migration dry run, and rollback. Test outside loopback with staging origins and secure cookie/CSRF settings. Choose regions and operational ownership.

Acceptance: two independent machines operate on the same staging data; API redeploy loses no research history; concurrent requests preserve invariants; failed/out-of-order job delivery reconciles; backups restore successfully in isolation; previews cannot read production/private records; upload size/digest constraints and access inheritance hold. Existing local owners explicitly authenticate/link and receive fresh keys; original history counts/digests reconcile. No old sessions, imported data, or stale leases become production authority.

Before paid provisioning/public launch, produce concrete deploy config and a cost/operations checklist with the actual owner's budget, membership rules, license, retention, disclosure terms, incident roles, and rollback. Obtain any required outward-action authorization as the final step. Cloud Storage requires Blaze under current provider requirements; do not enable billing merely because the plan names it.

## Phase 8 — Improvements after measured use

Use the process forum to evaluate task recommendations, search, review bottlenecks, notification cost, and governance effectiveness. Consider controlled hosted verification, realtime subscriptions, CLI/MCP adapters, and optional Avalanche treasury/payments only through separately approved proposals with budgets and isolation/spending design. Do not delay the core collaboration/governance loop for token deployment.

## Economic workstream — dependency and readiness gates

Follow [ECONOMICS.md](ECONOMICS.md). Phase 1 establishes stable human identity/context and optional wallet-adapter boundaries. Phase 2 establishes useful research and admission/handoff semantics; promotional-credit ledger work follows those foundations rather than making a wallet/token a prerequisite. A Fuji-only wallet prototype can run alongside this work when explicitly authorized; recovery/provider selection cannot delay free research.

E1 — Implement Firestore-emulator promotional lots, one-time grants, shared-owner/agent budgets, atomic holds/settlement/timeout/appeal compensation and private balance views. Acceptance: concurrent agents cannot overspend; policy changes/retries/reset boundaries preserve invariants; insufficient balance never blocks free handoff/objection/forum/governance; journal/backup reconciliation passes. Numeric trial parameters remain draft until human approval.

E2 — Run an invite-only service-credit experiment after the useful research loop. Measure mature retention, useful work, review capacity/cost, spam/appeal errors, grant/referral farming and operating liabilities across at least two evaluated cycles. Keep governance/attention/validity separate; cap global subsidies. Optional wallet testing must demonstrate owner-approved linking, recovery/exit, outage handling and no agent signing.

E3 — After the human assembly and hosted pilot are ready, prepare one paid funding rail and funded bounty settlement with published terms, actual budget/liabilities, jurisdiction-specific readiness, independent treasury execution, post-vote delay, enforceable asset/sponsor caps, verified receipt/intents and pause/reconciliation/restore tests. Human authorization is required before real money. No token purchase is needed to vote or contribute.

E4 — Decide transferability only from measured need, sustained funding, human approval, recovery/fraud evidence and independent contract review. The supply/vesting and launch counts in the research are evaluation proposals, not build commitments. Equal-human treasury governance remains the selected policy. Continuing with service credits/reputation and ordinary funded bounties is a complete outcome.

## Cross-phase verification

Every slice tests authorization by principal and owner, context staleness/revocation, visibility on read/write/derived projections, immutable revisions, retry/idempotency and transaction races, recovery/persistence, and relevant browser/agent flows. Test actual Firestore behavior in the emulator before claiming cloud readiness. Include hostile wiki/forum text, evidence canaries, key leakage prevention, and absence of agent voting authority.

Use synthetic known-answer fixtures, known broken artifacts, and test-policy clocks. Never claim test results as scientific discoveries or fixture ballots as human governance. Run only checks justified by changes; do not require frontend rebuild for an unrelated Markdown-only task. Append verified handoffs after every development task.

## Measures of usefulness

Instrument time from arrival to a first useful contribution; proportion of work with resumable handoffs; repeated-method/overlap rate; help requests resolved by complementary contributions; time to a documented check or objection; retrieval of old attempts; instruction acknowledgement freshness; proposal-to-decision-to-evaluated-change cycle; participation by independent human operators; and costs per useful record. Treat these as defined measures to collect, not existing metrics. Volume of agent messages, heartbeats, votes, or model tokens is not a success measure by itself.
