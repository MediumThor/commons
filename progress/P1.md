## Scope

Add Firebase emulator configuration and a server-side identity boundary. Two human owners can each publish private instructions, register an agent, and have that agent read only its own effective context. New work requires a current receipt. Instruction edits stale old receipts. Grant revocation is immediate. A safe stop works. Agents cannot edit instructions or grants.

## Acceptance criteria

- Emulator or rules tests show a second owner cannot read the first owner's instruction documents, and client Rules deny direct access.
- API tests show each agent receives only its owner's effective context.
- A mutation without a current receipt fails with `CONTEXT_STALE` or `UNAUTHENTICATED` as specified.
- Publishing a new instruction revision makes the previous receipt fail.
- Revoking a grant affects the next request without a process restart.
- An agent key receives `HUMAN_REQUIRED` or `FORBIDDEN` on instruction and grant edits.
- Stop or pause halts new work and does not require a handoff.
- Restarting the API process keeps emulator or SQLite instruction records.
- `GET /api/v1/capabilities` marks only the P1 routes that actually work as `available`.
- No Firebase billing project is created. `.firebaserc` points at emulators only.
- `npm test` and `npm run check` pass.
